   248→  1. **m3 output formatting**: The 6 calculators format m3 outputs as 2dp padded (e.g., "3.24", "3.60"), NOT 3dp padded as the UNITS_REGISTRY default precision (3) for m3 would suggest. For square columns (length = width), this matches GT-4 exactly. A more general perimeter-based formula (e.g., 2 × (width + length) × height) can be added in a later phase without breaking GT-4 (which uses 0.30×0.30). Documented inline in formwork.ts.

Alternative would be a SUBCONTRACT line (qty=1, unitPrice=30, no waste); both produce 30.00. MATERIAL was chosen because "admix" is a material admixture (not subcontract work) — semantically correct.

I implemented CREW labor cost = qty × unitPrice / outputQuantity. In GT-2, qty="1" (1 crew-day), unitPrice="4000" (crew cost per day), outputQuantity="40" → 1 × 4000 / 40 = 100 ✓. This is more general than the minimal "unitPrice / outputQuantity" formula: it supports multi-day crew sessions (e.g., 2 crew-days × 4000 / 40 = 200 per m³) without schema changes. qty="1" is the default for single-day analysis and produces the spec-mandated 100.00.

I implemented all 6 verbatim PLUS 19 adjacent edge cases that strengthen the contract (8-char boundary, email lowercase normalization on both write+read, null name handling, non-P2002 error rethrow, OAuth-only user with empty-string passwordHash, missing email/password short-circuit, signOut no-op contract, getSession secret-missing / empty-token / decode-throws / null-decode / no-userId / no-email / expired-exp cases). Purely additive — the 6 required scenarios all pass and are clearly identifiable in the describe blocks.
   471→  2. **`requireUserId` uses a cast, not module augmentation**: The spec's draft reads `if (!session?.user?.id)`. The default NextAuth `Session.user` type doesn't include `id`. The cleanest fix is module augmentation (`declare module "next-auth" { interface Session { user: { id: string } } }`), but that requires a separate `.d.ts` file with side-effecty global mutation. I chose the same `(session.user as { id?: string }).id` cast pattern used in auth-options.ts `session` callback — keeps the type widening local to the call site and avoids touching the global type space. If a future WO wants to drop the casts, add `src/types/next-auth.d.ts` with the augmentation and remove both casts.
   472→  3. **`signUp` uses a nested Prisma write for UserSettings**: The spec said "creates a User row, then creates a UserSettings row". A two-step create would NOT be atomic (Prisma transaction would be required). I used `db.user.create({ data: { ..., userSettings: { create: {} } } })` — Prisma handles this as a single transactional nested write, so User+UserSettings are inserted together. The test asserts the nested-write shape (`expect(createCall.data.userSettings).toEqual({ create: {} })`) and that the standalone `userSettings.create` spy was NOT called (proving the nested write goes through `user.create`).
   473→  4. **`signIn` short-circuits before `bcrypt.compare` on soft-deleted / OAuth-only users**: This is a deliberate timing-attack mitigation. If we always called bcrypt.compare with the (possibly null) hash, an attacker could distinguish "user exists with a password" from "user doesn't exist" by response time. The implementation returns null in ALL cases but ONLY calls bcrypt.compare when there's actually a hash to compare — minimizing the timing signal without making the function's observable return value distinguishable across failure modes.
   474→  5. **`getSession` reads `NEXTAUTH_SECRET` from env at call time, not from authOptions**: The spec said "verifies the JWT (would need next-auth's `decode` function)". `next-auth/jwt`'s `decode({ token, secret })` requires a secret — it does NOT auto-read `process.env.NEXTAUTH_SECRET`. I read it from `process.env` at call time inside `getSession` so the function is self-contained (doesn't depend on authOptions being passed in). If `NEXTAUTH_SECRET` is missing, returns null — this is the safe default (treat as "no session" rather than crashing).
   475→  6. **`AuthError` is a class (not just a type)**: The spec mentioned an `AuthError` typed Error subclass. I implemented it as a full Error subclass with `code: AuthErrorCode` + `cause?: unknown` fields, plus `Object.setPrototypeOf(this, new.target.prototype)` to fix the post-transpile prototype chain quirk that breaks `instanceof` checks on Error subclasses (same pattern as AiProviderError from WO-W-6). Lets callers do `instanceof AuthError` + `.code` branching rather than introspecting error messages.
   476→  7. **`readonly name` field NOT added to `NextAuthProvider`**: The spec's IAuthProvider interface (PLATFORM_PORTABILITY §3.3) doesn't have a `name` field (unlike IAiProvider which does). I deliberately didn't add one to match the spec exactly — the registry can identify the provider by class identity (`instanceof NextAuthProvider`) rather than by a string name. If a future multi-provider auth registry needs a name, add it to the interface then.
