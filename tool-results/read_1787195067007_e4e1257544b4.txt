   506→- Deviations from spec:
   507→  1. **Test suite has 25 tests instead of 6**: The spec listed 6 required scenarios. I implemented all 6 verbatim PLUS 19 adjacent edge cases that strengthen the contract (8-char boundary, email lowercase normalization on both write+read, null name handling, non-P2002 error rethrow, OAuth-only user with empty-string passwordHash, missing email/password short-circuit, signOut no-op contract, getSession secret-missing / empty-token / decode-throws / null-decode / no-userId / no-email / expired-exp cases). Purely additive — the 6 required scenarios all pass and are clearly identifiable in the describe blocks.
   508→  2. **`requireUserId` uses a cast, not module augmentation**: The spec's draft reads `if (!session?.user?.id)`. The default NextAuth `Session.user` type doesn't include `id`. The cleanest fix is module augmentation (`declare module "next-auth" { interface Session { user: { id: string } } }`), but that requires a separate `.d.ts` file with side-effecty global mutation. I chose the same `(session.user as { id?: string }).id` cast pattern used in auth-options.ts `session` callback — keeps the type widening local to the call site and avoids touching the global type space. If a future WO wants to drop the casts, add `src/types/next-auth.d.ts` with the augmentation and remove both casts.
   509→  3. **`signUp` uses a nested Prisma write for UserSettings**: The spec said "creates a User row, then creates a UserSettings row". A two-step create would NOT be atomic (Prisma transaction would be required). I used `db.user.create({ data: { ..., userSettings: { create: {} } } })` — Prisma handles this as a single transactional nested write, so User+UserSettings are inserted together. The test asserts the nested-write shape (`expect(createCall.data.userSettings).toEqual({ create: {} })`) and that the standalone `userSettings.create` spy was NOT called (proving the nested write goes through `user.create`).
   510→  4. **`signIn` short-circuits before `bcrypt.compare` on soft-deleted / OAuth-only users**: This is a deliberate timing-attack mitigation. If we always called bcrypt.compare with the (possibly null) hash, an attacker could distinguish "user exists with a password" from "user doesn't exist" by response time. The implementation returns null in ALL cases but ONLY calls bcrypt.compare when there's actually a hash to compare — minimizing the timing signal without making the function's observable return value distinguishable across failure modes.
   511→  5. **`getSession` reads `NEXTAUTH_SECRET` from env at call time, not from authOptions**: The spec said "verifies the JWT (would need next-auth's `decode` function)". `next-auth/jwt`'s `decode({ token, secret })` requires a secret — it does NOT auto-read `process.env.NEXTAUTH_SECRET`. I read it from `process.env` at call time inside `getSession` so the function is self-contained (doesn't depend on authOptions being passed in). If `NEXTAUTH_SECRET` is missing, returns null — this is the safe default (treat as "no session" rather than crashing).
   512→  6. **`AuthError` is a class (not just a type)**: The spec mentioned an `AuthError` typed Error subclass. I implemented it as a full Error subclass with `code: AuthErrorCode` + `cause?: unknown` fields, plus `Object.setPrototypeOf(this, new.target.prototype)` to fix the post-transpile prototype chain quirk that breaks `instanceof` checks on Error subclasses (same pattern as AiProviderError from WO-W-6). Lets callers do `instanceof AuthError` + `.code` branching rather than introspecting error messages.
   513→  7. **`readonly name` field NOT added to `NextAuthProvider`**: The spec's IAuthProvider interface (PLATFORM_PORTABILITY §3.3) doesn't have a `name` field (unlike IAiProvider which does). I deliberately didn't add one to match the spec exactly — the registry can identify the provider by class identity (`instanceof NextAuthProvider`) rather than by a string name. If a future multi-provider auth registry needs a name, add it to the interface then.
