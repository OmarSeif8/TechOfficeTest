   845→- Transaction pattern used for `applyToBoqItem()` (dual-write to RateAnalysis + BoQItem):
   846→  ```
   847→  async applyToBoqItem(id, boqItemId, expectedVersion) {
   848→    // 1. PRE-FLIGHT (outside transaction): fetch the analysis (need its totalRate
   849→    //    for the BoQItem.rate write). Return not_found if missing.
   850→    const analysis = await db.rateAnalysis.findUnique({ where: { id } });
   851→    if (!analysis) return { kind: "not_found" };
   852→
   853→    // 2. PRE-FLIGHT (outside transaction): verify BoQItem exists. Return not_found if missing.
   854→    const boqItem = await db.boQItem.findUnique({ where: { id: boqItemId } });
   855→    if (!boqItem) return { kind: "not_found" };
   856→
   857→    // 3. TRANSACTION: both writes commit together or neither does.
   858→    try {
   859→      const updated = await db.$transaction(async (tx) => {
   860→        // a. Optimistic concurrency on the analysis via updateMany (single SQL statement
   861→        //    with version in WHERE clause — atomic check-and-set).
   862→        const result = await tx.rateAnalysis.updateMany({
   863→          where: { id, version: expectedVersion },
   864→          data: {
   865→            boqItemId,           // set the link (idempotent if already set)
   866→            version: { increment: 1 },
   867→          },
   868→        });
   869→        if (result.count === 0) {
   870→          // Version mismatch — abort the transaction via sentinel throw.
   871→          throw new ConcurrencyConflict();
   872→        }
   873→        // b. Write the analysis's totalRate to the BoQItem's rate column.
   874→        //    This is the "apply" step — the BoQ now reflects the analysis.
   875→        await tx.boQItem.update({
   876→          where: { id: boqItemId },
   877→          data: { rate: analysis.totalRate },
   878→        });
   879→        // c. Fetch the updated analysis row to return.
   880→        return await tx.rateAnalysis.findUnique({ where: { id } });
   881→      });
   882→      return { kind: "ok", rateAnalysis: mapAnalysisToEntity(updated!) };
   883→    } catch (err) {
   884→      if (err instanceof ConcurrencyConflict) {
   885→        // Re-read to return currentVersion for caller's retry logic.
   886→        const existing = await db.rateAnalysis.findUnique({ where: { id } });
   887→        if (!existing) return { kind: "not_found" };
   888→        return { kind: "conflict", currentVersion: existing.version };
   889→      }
   890→      throw err;
   891→    }
   892→  }
   893→  ```
   894→  Key design points:
   895→  - Uses Prisma's interactive `$transaction(async (tx) => { ... })` form (not the array form) because we need to branch on `updateMany.count` mid-transaction.
   896→  - The `ConcurrencyConflict` sentinel class lets us abort the transaction cleanly (throwing inside the callback rolls back the entire transaction) and translate it to a tagged-union result in the outer function (instead of throwing to the caller).
   897→  - The analysis's `totalRate` is read in the PRE-FLIGHT step (outside the transaction) so we don't need to re-fetch it inside the transaction (we already have it cached in the closure). This is safe because `totalRate` is set at create time and only changed by `update()` — concurrent `update()` calls would bump `version`, causing the `updateMany` to fail with count=0 (which we translate to `conflict`).
   898→  - The BoQItem write does NOT version-check the BoQItem — the analysis is the source of truth for the rate; concurrent writers on BoQItem.rate will see the analysis-applied rate on next read. (If the BoQItem was concurrently deleted between our pre-flight and the transaction, the `tx.boQItem.update` would throw P2025 — the caller would see this as a Prisma error, which is acceptable for an unusual edge case.)
